## 1. 已確認的方向與本次範圍

課程主體是 **System Design**。AI Agent 是學習者進行需求分析、方案比較、查證與設計審查時的協作者，不是核心課程的設計對象。

重製遵循 [learning-map Skill](https://github.com/gcake119/learning-map/blob/main/SKILL.md)。本輪使用其金字塔原理檢查方式，從最高層能力、支撐能力、單元問題到可觀察學習目標逐層組織。金字塔是內容結構，不要求畫面一開始顯示完整課綱或所有結論。

本輪交付課綱提案與舊教材處理建議。課綱確認後才進入 Canonical Content → Content Review → Interaction Storyboard → Learning Copy → Implementation → Technical QA / Human Learning Review。每個單元的畫面、互動形式、動畫、控制項與螢幕數都尚未決定。

## 2. 目標受眾與深度：待確認的工作假設

適合已接觸軟體專案、能理解使用者畫面／API／資料庫基本角色，但尚未建立完整系統設計推理方式的學習者。可以使用 AI 協助開發，不要求能獨立閱讀整個 codebase 或手寫分散式系統。需要的 Web、請求回應與資料儲存基礎，以短導入補齊，不另外擴成程式語言課程。

深度定位：能解釋機制、比較方案、辨認限制、推演失敗、提出驗證依據。不是只認識名詞，也不以框架語法、雲端認證、面試答題模板或大規模平台實作為目標。

不預設百萬使用者、微服務或多區域部署。先提出符合已知需求的最小合理設計，再在負載、風險或需求改變時討論增添複雜度。

## 3. 最高層 learning outcome

> 面對一個真實工作需求，能在明示的限制與假設下，建立可被檢查的系統設計；能沿著資料與工作流程，說明正常、併發、失敗和改版時的行為，解釋設計選擇的理由、代價，以及需要哪些證據才能驗證它。

這裡的「系統保證」須有適用範圍、機制與假設；不能把畫出架構、測試通過或模擬成功當成對所有情況的正確性證明。

貫穿全課的推理鏈：工作情境 → 預期行為／限制 → 設計問題 → 機制與方案 → 驗證證據 → 重新評估條件。

## 4. 課綱金字塔：三大篇、八個核心單元、一個整合練習

```text
最高層：能建立、解釋、驗證並修正一個系統設計
│
├─ 第一篇：定義系統需要保證什麼
│  ├─ 1 從工作情境定義行為與限制
│  └─ 2 劃清系統邊界、責任與契約
│
├─ 第二篇：設計系統如何維持這些要求
│  ├─ 3 讓資料與狀態在併發下仍然正確
│  ├─ 4 決定工作的順序、等待與交接
│  └─ 5 處理失敗、重複與恢復
│
└─ 第三篇：用證據支持交付與演進
   ├─ 6 驗證行為，觀察與定位問題
   ├─ 7 依負載與瓶頸改善效能
   └─ 8 安全交付版本，維持資料與服務相容

整合練習：把這套推理用到另一種系統
橫貫條件：安全／隱私、成本／複雜度、設計取捨、AI 協作
```

這是學習順序，不是不可回頭的瀑布式開發。行為驗證與維運需求從單元 1 就提出；後段學習新的證據與機制時，必須能回頭修正需求、邊界和資料設計。Trade-off 不是留到結尾才處理的知識。

## 5. 各單元問題與 learning objectives

以下是能力與範圍提案，不是已通過 Content Review 的逐頁教材。

### 單元 1｜從工作情境定義行為與限制

**問題：使用者說「可以預約」，還缺哪些資訊才能開始設計？**

學完應能：

1. 把模糊需求整理為角色、前提、事件與可觀察結果，區分已確認規則、具體例子和待釐清問題。
2. 從正常、邊界、併發、未授權情境中，提出不得被破壞的規則，並指出哪些規則需要業務人員確認。
3. 區分功能行為與品質／營運限制；提出需要確認的使用量、等待時間、可接受停機／資料損失、敏感資料、成本與維運人力等條件。

必要概念：情境、業務規則、不變條件、驗收條件、品質屬性、負載假設。BDD / Example Mapping 是探索與表達需求的輔助方法，不以 Gherkin 語法作先備。

提議例子：兩人同時預約固定且容量為一的時段。不能直接把這個假設套到可重疊時段、多資源或容量大於一的系統。

學習結果：一份可討論的行為／限制清單，以及仍須求證的問題。來源：S-BDD、S-PRIMER、S-BYTE、S-AZURE。

### 單元 2｜劃清系統邊界、責任與契約

**問題：一次操作經過誰？每個地方承諾什麼、能做什麼？**

學完應能：

1. 沿著一次請求說明畫面、後端、資料儲存與外部系統的責任和資料流；區分邏輯模組、程序與獨立部署服務。
2. 為元件之間的互動定義輸入、輸出、錯誤與權限契約；指出資料與授權的信任邊界。
3. 在需求與維運限制下，比較模組留在同一應用或拆成服務的理由，不以元件數或微服務數衡量設計完整性。

先備：單元 1。必要概念：系統邊界、責任、依賴、API／契約、身分與授權、伺服器端檢查、模組與服務的差別。

提議例子：畫面送出預約、後端檢查、資料保存與外部通知。檢查使用者是否可修改另一人的預約。

學習結果：系統責任與信任邊界圖、关键互動契約。來源：S-BYTE、S-PRIMER、S-AZURE、S-AWS-SEC。

### 單元 3｜讓資料與狀態在併發下仍然正確

**問題：兩個請求都看到「還有空位」，為什麼可能做出互相衝突的更新？**

學完應能：

1. 為主要資料指定權威來源與修改責任，區分持久資料、暫存副本、讀取模型及任務進度；畫出狀態與合法轉移。
2. 推演兩個操作交錯執行時如何破壞規則，說明先查再寫為什麼需要檢查原子性與隔離條件。
3. 依資料模型比較約束、交易與併發控制的作用和限制；辨認哪些資料必須立即一致、哪些允許暫時落後。

先備：單元 1、2。必要概念：資料模型、識別、狀態所有權、交易邊界、原子性、隔離、併發衝突、讀取時效。資料庫機制須依所選資料庫及隔離等級核實，不教「包成 transaction 就萬無一失」。

提議例子：預約建立與取消、兩個請求爭取同一時段、顯示清單與保存狀態不同步。

學習結果：關鍵資料模型、狀態轉移與併發保護說明。來源：S-BYTE、S-DDIA、S-MIT；必要細節以 S-PG 核實。

### 單元 4｜決定工作的順序、等待與交接

**問題：哪些事要當場完成，哪些可以之後處理？「收到」和「完成」如何區分？**

學完應能：

1. 從工作依賴與回應要求判斷同步、非同步、串行與平行，不把「可以拆」直接等同「應該拆」。
2. 為背景工作定義已接受、處理中、成功、失敗及結果回報方式，區分訊息入列、工作執行與業務完成。
3. 定義交接所需的識別、資料版本、狀態、錯誤與權限資訊，指出持久交接及順序要求。

先備：單元 2、3。必要概念：呼叫與訊息、依賴、背景工作、佇列、交接契約、結果查詢／回報、順序。

提議例子：預約成立後發通知；通知是否是「預約成功」的必要條件由單元 1確認。也可使用旧案例「收到附件」與「完成歸檔」對比。

學習結果：工作流程與交接／完成契約。來源：S-BYTE、S-AZURE-QUEUE、舊版狀態與交接案例。

### 單元 5｜處理失敗、重複與恢復

**問題：操作已經送出卻沒收到回覆，系統現在知道什麼？下一步怎麼做？**

學完應能：

1. 區分明確失敗、暫時故障、結果未知及部分成功，逐條依賴推演故障影響。
2. 依操作性質比較查證、有限重試、退避、冪等、停止與人工接手；說明重試預算與冪等的實際支援範圍。
3. 為重要故障提出隔離、降級與恢復方案，辨認備援、備份、還原及補償的不同用途，保留已完成效果與未知狀態。

先備：單元 3、4。必要概念：timeout、partial failure、retry budget、idempotency、故障隔離、fallback、backup／restore。斷路器與 outbox 可在相應問題下延伸，不以學會名詞取代機制推理。

提議例子：建立預約成功但回應遺失；預約保存成功但通知失敗；資料還原是否達到原先可接受的資料損失與恢復時間。

學習結果：失敗情境、可觀察狀態、處理方式與恢復責任表。來源：舊版 reliability、S-AZURE-RETRY、S-MIT、S-AWS。

### 單元 6｜驗證行為，觀察與定位問題

**問題：怎麼確認要求有做到？出問題時，哪些證據能判斷發生了什麼？**

學完應能：

1. 把單元 1的行為與限制對應到設計機制、適當測試及上線後可觀察的證據，辨認沒有被驗證的假設。
2. 區分不同範圍的自動測試與 production 觀測；說明 logs、metrics、traces 各能回答的問題與限制。
3. 從正常、邊界、併發、故障及未授權案例檢查成果與過程，選擇必要紀錄、關聯識別與敏感資訊保護方式。

先備：單元 1–5。必要概念：驗收、契約／整合／端到端檢查、執行證據、品質指標與目標、可觀測性、回歸案例。BDD 以協作釐清行為；TDD 以測試引導實作；兩者都不等同「所有測試都是 E2E」。

提議例子：API 回覆成功，但沒有形成有效預約；通知沒有送達，要區分根本沒排程、尚未處理與外部服務失敗。

學習結果：需求—機制—驗證證據對照，以及基本觀测計畫。通過測試與觀測正常都不宣稱覆蓋所有可能行為。

來源：舊版 evidence、S-BDD、S-AZURE-OPS、S-AWS。

### 單元 7｜依負載與瓶頸改善效能

**問題：系統慢在哪裡？增加快取、工作者或主機實際改變什麼？**

學完應能：

1. 用明示假設估計請求量、尖峰、資料量與工作處理速度，區分延遲、吞吐量、等待與資源飽和。
2. 依量測證據比較查詢／索引調整、快取、平行、批次、佇列與水平擴展，描述改善的路徑及可能轉移的瓶頸。
3. 用同一组行為與品質基準，檢查改動後的正確性、時效、延遲、容量與成本；能說明何時不需要額外元件。

先備：單元 3–6；負載需求已在單元 1提出。必要概念：baseline、瓶頸、快取時效、尖峰與平均、backpressure、無狀態與擴展。基本區分複寫與分割解決的問題，深入共識、分片演算法及跨區域部署列為延伸。

提議例子：大量查詢可預約時段；快取顯示資料與權威寫入檢查的不同責任；工作流入速度持續高於消費速度。

學習結果：一次有基準、有依據、有代價與撤回／重估條件的改善提案。來源：S-BYTE、S-DDIA、S-AZURE-CACHE、S-AZURE-QUEUE。

### 單元 8｜安全交付版本，維持資料與服務相容

**問題：新版程式、舊版程式與既有資料同時存在時，怎麼更新而不破壞已承諾的行為？**

學完應能：

1. 區分建置、測試、產物、發布與部署，說明環境／設定／秘密資料管理，以及 CI/CD 在交付證據中的責任。
2. 推演 API 或資料格式改動對舊新版元件的影響，提出相容性、migration 順序與版本演進策略。
3. 依可用性與風險要求比較逐步發布、回復舊版或向前修正，定義上線驗證、停下來的條件與資料恢復方式。

先備：單元 2、3、5、6；效能與成本取捨可回用單元 7。必要概念：可重現交付、版本、相容、migration、rollout、rollback、forward fix、恢復驗證。區分 Continuous Delivery 與 Continuous Deployment，不把 CD 一律解釋為無人核准的自動正式部署。

提議例子：預約狀態新增值或資料欄位改名；舊版程式能否讀取新版已寫入的資料。回復程式版本不自動等於復原所有資料變更。

學習結果：相容性與交付／恢復計畫。不要求撰寫 GitHub Actions YAML、Dockerfile、Terraform 或 Kubernetes manifest。

來源：S-BYTE、S-AZURE-OPS、S-AZURE-EVOLUTION、S-AWS、S-DDIA（版本相關章節待精讀）。

## 6. BDD、AI 與安全的橫貫位置

### BDD：需求入口與驗證回收

單元 1以角色協作、規則、例子、疑問釐清期待；單元 6再把这些期待對應到測試與觀測。這是將 BDD 的方法用於本課程的教學設計，不宣稱完整涵蓋 BDD。

使用者提供的五張 AI Coding／Skills／SDD／TDD／BDD 課綱截圖，角色是 **curriculum reference**。只據可見標題參考「從行為、規格到實作驗收的銜接」。未取得影片或講義，不能宣稱讀過其實際教學，不能把課程特定的 Truth／Plan、4+2、slash commands 視為業界共同標準。

Cucumber 官方 BDD 與 Example Mapping 文件補作方法定義來源，列為第二層的窄範圍補充，不增加新的課程主線。

### AI：幫助推理，保留人的判斷責任

每單元可讓 AI 提出待釐清問題、整理條件、比較方案、產生反例或協助解讀證據。學習者需能辨認：輸入是否足夠、哪些是猜測、來源是否支持、設計是否滿足需求、驗證還缺什麼。

建議分開記錄「已確認需求與規則」「設計假設與決策」「實作與驗證計畫」。這是本課程的工作材料分類，不宣稱出自參考課程的完整 Truth／Plan 定義。

本提案不要求為教材串接即時模型、不要求 API key，不承諾自動評分或自動通過驗收；AI 協作如何出現在互動教材裡，留待後續 storyboard 決定。模型架構、RAG、MCP、模型後訓練與多 Agent 編排均非核心單元。

### 安全：從需求開始的限制

不能只在最後的架構 review 才檢查安全。單元 1辨認角色、資料敏感度與禁止行為；單元 2建立信任與授權邊界；單元 3、4檢查資料和交接權限；單元 5避免故障恢復繞過授權；單元 6控制紀錄中的敏感資料；單元 7檢查共享快取與資源限制；單元 8處理環境隔離與 secrets。

這是系統設計基本要求，不擴成獨立滲透測試或資安工具課。

## 7. 整合練習與可轉移能力

提議以「場地預約與通知」作最小貫穿案例，以「批次文件匯入、核對與通知」作不同領域的整合練習。皆為合成教學情境，不包含真實個案或使用者專案內部資料。

整合練習提供需求、限制與部分證據，不預先提供可直接套用的完整架構。學習者應能提出關鍵問題、定義狀態與契約、比較失敗與負載處理、安排驗證和交付，並解釋取捨。

確認理解的依據：

- 能把一項需求追到責任、資料、機制與證據；
- 能預測一個未看過的併發、故障或版本變動情境；
- 能指出設計尚未支持的要求或待查證假設；
- 能在需求改變時修改設計，說明代價，而不是照抄原範例元件。

學習成果可逐步累積成一份設計說明，不要求一次填完大型文字表單，也不先決定介面型態。沒有新增評分、解鎖或學習完成閘門。

## 8. 舊版七單元處理建議

本輪核對 `learning/curriculum.mjs`、`learning/deep-content.mjs` 與 `docs/guided-learning.md`。舊內容已有任務契約、固定流程比較、狀態恢復、資訊時效與交接契約；不能把原本的缺口一概描述成「完全沒有」。主要問題是這些概念以 Agent 為中心展開，系統需求、資料機制與交付演進未形成新的主線。

下表的處理是 **提案**。「刪除」指不再列為新核心課程內容，不代表本輪刪除檔案、歷史版本或舊路由。

| 舊單元 | 保留 | 移動／改寫 | 從新核心課程刪除 |
| --- | --- | --- | --- |
| overview：先看完整系統 | 任務範圍、完成條件、責任與限制 | 移至 1、2；改寫為使用者工作與系統契約 | 以 LLM／工具／context 構成完整系統的必修開場 |
| loop：讓任務持續推進 | 狀態轉移、依賴、保存進度、停止與恢復 | 移至 3、4、5；轉成業務／背景工作狀態 | 把 observe–decide–act 迴圈當作一般系統設計主骨架 |
| context：適當資訊 | 來源、版本、過期、狀態差異 | 資料部分移至 3、7；AI 設計脈絡與摘要移至協作補充 | Token 預算、提示詞壓縮、RAG 作為通用系統設計必修 |
| reliability：可控失敗 | timeout、未知結果、有限重試、冪等、部分成功、fallback | 核心移至 5；資料驗證移至 2、3；擴充系統依賴與恢復 | 只改 Agent 敘述但沒有機制與邊界的新版本 |
| evidence：證據驗收 | 成功條件、過程與成果分開驗證、trace、回歸、敏感資訊 | 成功條件前移至 1，主要內容改寫至 6；從 Agent trace 擴至系統證據 | 以 LLM judge 校準作所有系統的核心驗收方式 |
| optimization：量測改善 | 基準、延遲、平行依賴、比較條件與成本 | 移至 4、6、7；重心轉成負載與系統瓶頸 | 把減 Token／換小模型作為一般系統優化主線 |
| multi：分工取捨 | 責任、交接欄位、版本、錯誤傳遞、協調成本 | 系統契約移至 2、4；多角色 AI review 移至協作補充 | 單／多 Agent 架構比較作為全課最後必修章 |

可保留的深層素材包含既有 designBriefs 的任務契約、執行／狀態設計、失敗處理表、驗收／觀測方案、改善實驗與交接契約。但必須依新 learning objectives 重新選取與查證，不能把文字欄位或舊互動直接當成新教材。

需要新增／補強：需求探索、品質需求、信任邊界、資料模型與交易／併發、同步／非同步的完成契約、系統負載分析、部署相容、資料遷移與恢復。

現有 79 個情境、七個入口動畫、SystemLab、設計工作台與 Token Profiler 都是可審查資產，不是新課程的數量或介面要求。Token Profiler 的教學節奏可作 reference；它的 Agent／Token 內容不因此自動留在核心。

## 9. 金字塔檢查結果

- **主線**：三篇分別回答「需要保證什麼」「用什麼機制維持」「用什麼證據支持交付與變更」，都支撐最高層設計能力。
- **分組**：同層用設計問題區分，而不是混列產品名、元件名、品質屬性與開發工具。
- **順序**：先有需求與邊界，再討論狀態；有狀態和交接，才推演部分失敗；先學基本驗證與觀測，再用量測做優化；最後處理版本與資料演進。
- **重複控制**：單元 3談資料正確性，4談工作協調，5談不如預期時如何處理，6談如何取得與判讀證據；同一案例可以重訪，但不能重講同一結論。
- **必要補強**：安全、營運限制與驗證需求從第一篇出現，不延到結尾。BDD 用來跨越模糊需求到可檢查行為的落差。
- **深度控制**：核心採「問題→機制→比較→邊界→應用」；共識協定證明、深層資料庫實作、跨區域架構、完整 BDD framework 與 CI/CD 工具設定留作延伸。
- **驗證限制**：本轮完成的是來源支持的結構與範圍提案；不宣稱所有來源已全文精讀、所有教材內容已核實，或學生已通過學習驗收。

## 11. 目前的確認點

使用者需要確認的是學習目的與深度是否適用、三篇八單元的學習路徑是否符合需要，以及貫穿／轉移案例是否合適；不要求初學者負責認證學科完整性。

尚未確認的項目：單元結構與順序、案例選擇、核心／延伸深度分界。

確認後，才以此版本建立逐單元 Canonical Content 與來源對照，再做 Content Review。未確認前，不進入互動 storyboard、畫面文案或實作。
